1
每日 AI 热点 Top10 飞书私聊推送
类型:主动推送 + 定时任务 · automation-1780795727451
ACTIVE
链路
WebSearch 全网 AI 新闻 → 按热度×重要性排序去重 → 选 Top10 → 通过 lark-cli im +messages-send 推送至本人飞书私聊
关键命令
lark-cli im +messages-send --as bot --user-id ou_7c6a... --markdown "..."
触发频率
每天 09:00 · FREQ=DAILY;BYHOUR=9;BYMINUTE=0
踩坑修正
--as user 缺 im:message.send_as_user scope 会失败,改用 --as bot 跑通(前提:user 已与 bot 建立过 P2P 会话)
实测结果
手动跑通一次,message_id om_x100b6d78f03524a0c2992c72c542933,飞书私聊已收到 Top10 推送(含 Anthropic IPO、Claude Opus 4.8、DeepSeek 融资等当日要闻)
2
吴晓波飞书对谈(知识库 RAG + 准实时轮询)
类型:被动响应 + 知识库 RAG · automation-1780811241203
ACTIVE
链路
每 5 分钟拉取飞书 P2P 会话 → 筛「吴老师 xxx」未回提问 → 调用 lke-kb 检索吴晓波知识库(25318 篇) → 按 wuxiaobo-skill 5 段式生成 → messages-reply 引用回复
关键命令
lark-cli im +chat-messages-list --chat-id oc_xxx --sort desc --as bot
lark-cli im +messages-reply --message-id om_xxx --as bot --markdown "..."
触发频率
每 5 分钟,8:00–24:00 · FREQ=HOURLY;BYMINUTE=0,5,10,...,55
关键洞察
实时监听 event consume 因 IPC socket 被 Agent 沙盒拦死,转用「主动轮询拉历史消息」走纯 HTTP 绕开沙盒。靠 reply_to 字段去重防刷屏。
实测结果
已成功回复用户 2 条提问:「企业出海还有机会吗」(命中 246 篇,引《大周期与企业出海机会》)、「黄金还值得买吗」(走红线模板,转长周期货币逻辑)
3
日程创建与改期(下周二 8:00–10:00 和 tic 开会)
类型:日历回写 · event_id 561646e2-...
已写入
链路
自然语言「下周一上午 8-10 点和 tic 开会」 → 用 date 命令换算精确时间戳 → +create 写入主日历 → 用户改期 → +update 移到下周二 → 二次 +agenda 回查确认
关键命令
lark-cli calendar +create --summary "..." --start "2026-06-09T08:00:00+08:00" --end "..." --as user

踩坑修正
①时间字符串↔时间戳必须用系统命令算,不能口算 ②event_id 要用带 _0 后缀的完整形式,从 +agenda 返回值拿 ③通讯录搜不到「tic」,与会人未自动加,仅标题注明
实测结果
回查 6/9(下周二)有日程、6/8(原下周一)已空,飞书日历 App 立刻可见,自动附带飞书会议链接
4
本地 docx 上传飞书并转在线云文档
类型:文件回写 · token Qbfxd8yvCo1YVpxb3AIcz52Nnrd
已完成
链路
本地 docx → cp 到工作目录(CLI 约束) → drive +import --type docx 转飞书在线云文档 → 落入云盘根目录,可在线阅读、检索、评论
关键命令
lark-cli drive +import --file ./AIagent发展及Workbuddy应用交流.docx --type docx --name "..." --as user
两条路对比
+upload 当附件传(下载才能看) vs +import 转在线文档(可读可检索可评论,更适合知识库)。本案选后者。
重要纠错
最初判断「user 缺 wiki scope 需重新授权」是误判。auth status 实测 user token scope 已含 wiki:space:retrieve/write_only、wiki:node:create 全套,只是 token 处于 needs_refresh 状态,触发任意 user API 即自动刷新。真实瓶颈是「账号下还没建过 Wiki 空间」(见案例 5)。
实测结果
导入成功,URL kcnij01rty0f.feishu.cn/docx/Qbfxd8yvCo1YVpxb3AIcz52Nnrd 可直接打开。后续在案例 5 中已挂进新建的 Wiki 知识空间。
5
新建 Wiki 知识空间并挂载文档
类型:Wiki 知识库回写 · space_id 7648603751674023100
已完成
链路
触发 user token 自动刷新 → wiki +space-create 新建「WorkBuddy 实践库」空间 → wiki +move --obj-token --obj-type docx 把云盘 docx 转挂到 Wiki 节点 → +node-list 回查确认
关键命令
lark-cli wiki +space-create --name "WorkBuddy 实践库" --description "..." --as user
lark-cli wiki +move --obj-token Qbfxd8yvCo1YVpxb3AIcz52Nnrd --obj-type docx --target-space-id 7648603751674023100 --as user
两步式分工
+space-create = 创建知识空间(返回 space_id);+move = 把已有云盘文档挂进 Wiki 节点(返回 wiki node_token)。docx 的 obj_token 不变,但增加了 wiki 视图入口。
未尽项
空间默认 visibility=private,改为「对组织开放」需在飞书 UI 里点(lark-cli 未封装 spaces setting 命令,避免 OpenAPI 误改敏感配置)
实测结果
空间 7648603751674023100 + 节点 ZZ6Nw7dneiNs1nkB6Jcckl1An6e 已建立,直达链接 kcnij01rty0f.feishu.cn/wiki/ZZ6Nw7dneiNs1nkB6Jcckl1An6e,飞书侧边栏「知识库」可见
ARCHITECTURE

统一链路架构

所有飞书联动案例都走同一条标准链路:WorkBuddy(Agent + Skill)→ MCP Connector → lark-cli/HTTP API → 飞书开放平台。差别只在中间「数据来源」和最后「触达接口」。

Step 1 · Trigger
触发源
用户对话 / Automation 定时 / 飞书消息轮询
Step 2 · Brain
WorkBuddy
Skill + MCP 工具 (WebSearch / lke-kb / adp-kb)
Step 3 · Bridge
飞书 Connector
lark-cli (28 个 lark-* skill, 用户/bot 双身份)
Step 4 · Action
飞书侧落地
IM / 日历 / 云文档 / Wiki / 视频会议
⚠ 已知边界(诚实披露)
1. 实时事件监听走不通。 lark-cli event consume 需要在本地建 IPC socket 与 bus.fork.lock,Agent 沙盒会拦截 operation not permitted,即使父进程提权,spawn 出的子进程仍被沙盒限制。解法:改用「轮询拉取历史消息」走纯 HTTP API,绕开沙盒(吴晓波对谈案例已验证可行)。代价是「秒回」变成「最长延迟 N 分钟」。

2. Wiki 知识库无现存空间时需先建。 用户首次接入 Wiki 时,wiki +space-list 可能返回 0 个空间。这并非权限缺失(auth status 实测 user token scope 已含 wiki 全套),而是账号下确实没建过空间。解法:用 wiki +space-create 直接建一个,再用 wiki +move 把云盘文档挂进去(本报告案例 5 已实测打通)。

3. Automation RRULE 不支持 MINUTELY。 最细粒度是 HOURLY。要实现「每 N 分钟」需用 FREQ=HOURLY;BYMINUTE=0,5,10,...,55 + BYHOUR=列举 来模拟。

4. 通讯录搜索是模糊匹配,但要求是飞书全名/手机/邮箱。 别名(如「tic」)搜不到,需要用户提供准确字段才能解析为 open_id 加为与会人。
