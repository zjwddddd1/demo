WorkBuddy 项目功能
产品需求文档（PRD）

以「项目」为容器，将成员协作、资料库、事项/待办与贯穿需求全流程的 AI 助手整合为一体，让产品团队在同一空间内完成从需求规划到上线复盘的完整闭环。

版本v1.0 目标用户产品 / 项目团队 视角AI 产品经理 规范EARS 状态待评审

1. 背景与问题 ▾

产品团队的日常协作被割裂在多个工具中：需求文档散落在网盘，任务追踪在项目管理软件，评审结论沉在聊天记录，AI 工具又是独立的对话窗口。信息无法沉淀为「项目上下文」，导致以下痛点：

痛点具体表现影响
上下文断裂PRD、设计稿、评审结论、Bug 分散在不同工具，AI 无法感知项目全貌反复解释背景，AI 产出通用而不贴合
流转靠人肉阶段成果依赖人工通知与转发关键角色漏接信息，交付物脱节
过程不可追溯决策、变更、责任人缺乏统一记录复盘困难，重复踩坑
AI 能力孤立AI 只能对话，不能读资料、建事项、触达成员AI 停留在「聊天」而非「协同」

2. 产品目标 ▾

产品愿景

让 WorkBuddy 项目空间成为产品团队的统一协作容器与 AI 上下文中枢——所有资料、事项、成员与 AI 助手在同一项目内联动，AI 天然理解「这个项目正在做什么、由谁负责、到了哪个阶段」。

目标拆解

层级目标衡量方式
业务目标缩短需求全流程协同周期，减少信息流转损耗需求平均交付周期 ↓、跨阶段返工率 ↓
用户目标产品经理在一个空间内完成规划到复盘单项目跨阶段工具切换次数 ↓
AI 目标AI 基于项目上下文自动生成交付物并驱动流转AI 产出采纳率、AI 触发的事项创建量
本期不做：跨项目组合视图、复杂甘特图排期引擎、财务/预算模块。聚焦「单项目内全流程协同 + AI 中枢」。

4. 用户故事 ▾

US-01 项目搭建

作为产品经理，我希望创建项目并邀请成员，让所有协作在统一空间内进行。

US-02 AI 需求规划

作为产品经理，我希望 AI 基于项目资料帮我梳理需求池与优先级。

US-03 PRD 协同

作为产品经理，我希望用 AI 按 EARS 规范写 PRD 并上传资料库供评审。

US-04 成果流转

作为产品经理，我希望一键创建评审事项、分配责任人并添加关注人。

US-05 研发跟进

作为研发负责人，我希望把需求拆成子任务并附上 PRD 按依赖推进。

US-06 测试验收

作为测试，我希望基于 PRD 生成用例，发现问题创建 Bug 并回链需求。

6. 功能清单（EARS 需求描述） ▾

点击下方标签筛选不同 EARS 类型的需求条目。

EARS 筛选： 全部 Ubiquitous 恒定 Event-driven 事件 State-driven 状态 Optional 可选 Unwanted 异常

M1 项目空间

Event-driven

When 用户点击「创建项目」并填写名称，the system shall 生成独立项目空间并将创建者设为 Owner。

Ubiquitous

The system shall 始终为每个项目维护一份「项目指令/上下文」，供 AI 在本项目内所有对话中读取。

Optional

Where 项目已归档，the system shall 置为只读并从活跃列表隐藏，但保留全部资料与事项可追溯。

Unwanted

If 项目名称为空或重名，then the system shall 阻止创建并给出明确错误提示。

M2 成员与权限

Event-driven

When Owner 邀请成员并指定角色，the system shall 发送邀请并在接受后按角色授予权限。

State-driven

While 成员为「关注人」，the system shall 在其关注的事项或文档变更时推送通知。

Unwanted

If 非授权成员尝试删除他人事项或资料，then the system shall 拒绝并记录该行为。

M3 项目资料库

Event-driven

When 用户上传 PRD/设计稿/评审结论/测试用例，the system shall 存入资料库并纳入 AI 可检索的上下文。

Ubiquitous

The system shall 为同名文档保留版本历史，允许查看与回溯。

Unwanted

If 文件超限或格式不支持，then the system shall 中止上传并提示允许的格式与上限。

M4 事项 / 待办

Event-driven

When 用户创建事项并指定负责人，the system shall 生成事项、通知负责人，并支持附加文档与关注人。

State-driven

While 事项处于「进行中」，the system shall 允许拆子任务、设依赖并汇总完成度。

Ubiquitous

The system shall 始终记录事项状态流转历史以供追溯。

Unwanted

If 事项被标记完成但仍有阻塞性子任务，then the system shall 弹出确认并提示风险。

M5 AI 全流程协同助手（核心）

阶段AI 能力产出物
① 需求规划梳理用户/痛点/场景、竞品调研、优先级建议需求概要、需求池、优先级、待确认清单
② PRD 撰写按 EARS + 标准结构撰写、补全边界/权限/埋点结构化 PRD（MD/Word/HTML）
③ 设计/研发评审整理议题、依赖、风险，拆页面/状态/技术依赖议题清单、风险清单、待办问题
④ 研发跟进拆研发任务与依赖，汇总进度与风险任务拆解、进度摘要、风险清单
⑤ 测试验收基于 PRD 生成用例、规范 Bug、判断阻断性测试用例、Bug 事项、验收/风险清单
⑥ 上线复盘总结达成、遗留问题、提炼可复用经验复盘报告、数据观察、后续行动项
Ubiquitous

The system shall 始终基于当前项目的资料库、成员与事项上下文生成回答，而非通用回答。

Event-driven

When AI 完成某阶段交付物，the system shall 主动提醒「上传资料库 / 建下一环节事项 / 加关注人」。

Event-driven

When 用户确认，the system shall 由 AI 代建事项、附交付物并分配给负责人。

Unwanted

If 信息不足（缺目标用户/数据口径），then the system shall 先追问关键缺口，不得编造结论。

Unwanted

If 涉及排期/资源/上线范围，then the system shall 提示用户找对应负责人确认，而非自行拍板。

M6 通知与流转

Event-driven

When 事项被分配、状态变更或被 @，the system shall 向负责人与关注人发送通知。

State-driven

While 某阶段成果已就绪，the system shall 提示可流转至下一环节角色，并附交付物链接。

7. 核心流程说明 ▾

7.1 需求全流程主线

STAGE 1
需求规划
AI 梳理需求池 → 建需求事项
STAGE 2
PRD 撰写
AI 写 PRD → 上传 → 建评审事项
STAGE 3
评审
整理议题/风险 → 结论沉淀 → 拆待办
STAGE 4
研发跟进
拆研发任务 → 附 PRD → 进度摘要
STAGE 5
测试验收
生成用例 → 提 Bug → 回链需求
STAGE 6
上线复盘
复盘报告 → 优化点转新事项

7.2 「AI 生成 → 成果流转」子流程

  1. 用户在项目内向 AI 发起某阶段任务（如「写 PRD」）。
  2. AI 读取项目资料库 + 事项 + 成员上下文生成交付物。
  3. 信息不足时 AI 先追问，补齐后再产出。
  4. 产出后 AI 主动提醒：上传资料库 / 建下一环节事项 / 加关注人。
  5. 用户确认 → AI 执行：写入资料库、创建并分配事项、附交付物、通知角色。

8. 交互与权限说明 ▾

8.1 权限矩阵

操作Owner产品经理普通成员关注人
管理成员/权限✅➖ 可邀请❌❌
创建/删除项目✅❌❌❌
上传/管理资料✅✅✅👁 只读
创建/分配事项✅✅✅ 自建👁 只读
接收通知✅✅✅✅

8.2 关键交互原则

  • AI 动作需用户确认：创建事项、分配、上传等外部动作前先说明再执行。
  • 上下文透明：AI 回答时可标注所依据的项目资料，便于溯源。
  • 流转不强制：AI 只提醒流转，是否执行由用户决定。
